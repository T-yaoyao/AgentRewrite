1. Cost Efficiency
- Overall cost change: The top-level cost rose from 3,088,689.67 (original) to 16,156,228.14 (rewritten/enhanced), an increase of approximately +423% (~5.2x). On paper this is a significant regression, but it must be interpreted together with the fact that the rewritten query returns up to 100 rows instead of 1 and that the optimizer's estimates for the original correlated plan (rows=1 throughout) are likely severe underestimates; actual runtime of the original plan could be far worse than its nominal cost suggests.
- Cost at the most expensive node: In the original plan, the cost hotspot is the Parallel Hash Anti Join subtree (~3,087,443), driven by two parallel scans of lineitem. In the rewritten plan, the hotspot shifted to the aggregation pipeline: the inner GroupAggregate over lineitem (starting from a Sort costing ~14,842,568 up to ~14,987,450) now dominates. The cost center moved from "join over raw lineitem scans" to "sort + group 57.95 million lineitem rows."

2. Plan Characteristics
- Scan type transitions: Both plans still use Seq Scan on lineitem and supplier and a trivial Seq Scan on nation (single-row filter). The original plan performs two Index Scans per candidate row — lineitem_pkey (l2) and orders_pkey — inside Nested Loops; the rewritten plan removes the per-row lineitem index probe entirely, and replaces the per-row orders_pkey probe with a single Parallel Seq Scan on orders used to build the qualifying order-key set. The only remaining index access in the rewritten plan is one clean Index Scan on supplier_pkey to fetch the final supplier attributes.
- Join algorithm refinements: The original Nested Loop Semi Join + Parallel Hash Anti Join (correlated "exists another supplier with later receipt" pattern) is replaced by a declarative set-based formulation: a Hash Join between the full lineitem table and a Unique/Gather-Merge derived list of ~386,548 qualifying order keys, followed by GroupAggregate with count(DISTINCT ...) filters. This converts repeated semi-join probing into a single bulk join and aggregation.
- Sorting and intermediate results: The original plan contains only two small final sorts. The rewritten plan introduces one very large intermediate Sort (~57.95M rows, width 16) feeding the per-order GroupAggregate, plus a moderate Sort/Gather Merge (~386K order keys). This is the main structural cost: the rewrite trades many tiny correlated probes for one large batched sort. The final output stage (Sort + GroupAggregate over ~667 supplier rows) remains cheap and identical in shape in both plans.

3. Resource Utilization
- Memory/Hash usage: The original plan builds two large Parallel Hash tables, each sized for ~8.33M filtered lineitem rows — a substantial memory footprint executed concurrently. The rewritten plan's hash tables are much smaller (~386K order keys in the upper join; ~331K lineitem rows and ~2.3K suppliers in the inner parallel joins), substantially reducing concurrent hash memory. However, it adds a single-threaded sort of ~57.95M rows, which carries a high risk of external merge / disk spill that the optimizer cost partially reflects.
- Worker count: Both plans use 2 parallel workers. In the original, workers feed a Gather over the anti-join; in the rewritten, workers feed a Gather Merge over the sorted qualifying-order-key derivation. Parallelism is preserved, but in the rewritten plan the heaviest node (the 57.95M-row Sort + GroupAggregate) executes outside parallel workers, which is a parallelism-efficiency drawback.

4. Other Improvements
- The enhanced plan is identical to the rewritten plan (same structure, same costs, same row estimates), so no incremental benefit was obtained at the plan level; the rewrite step already converged to the planner's chosen execution.
- Robustness benefits of the rewrite: it removes the correlated subquery (which was producing rows=1 estimates in the original — a likely cardinality misestimate), making the plan less sensitive to estimation errors; it uses an aggregate with FILTER clauses to compute the "late-shipment" condition declaratively; and it resolves supplier ambiguity deterministically via max(l_suppkey) with a single key-based Index Scan on supplier_pkey.
